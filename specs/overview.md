# SSD 规范驱动开发 — 全景概述

> 本文档是 SSD (Spec-Driven Development) 方法论的完整答卷，回答从"为什么做"到"做得怎样"的全部问题。

---

## 1. 背景：什么项目、什么约束

### 1.1 项目定义

**MP-SDK** 是一套跨平台 JSBridge SDK 框架，服务于金融/会员业务场景。核心使命：解决 WebView 容器中 Native → Web 大数据量传递的时序问题，同时为 Android / HarmonyOS / Web 三端提供统一的桥接通信与数据同步能力。

| 维度 | 说明 |
|------|------|
| **业务场景** | 金融借贷 + 会员服务，WebView 页面需携带用户认证/借款/会员数据 |
| **核心机制** | 等待唤醒数据同步 — 请求阻塞直到 Native 数据就绪 |
| **技术方案** | Proto 驱动 Codegen + JSBridge 双协议适配 + KSP 编译期注入 |
| **产出物** | Android AAR + 鸿蒙 HAR + 前端 TGZ（npm 包） |

### 1.2 约束条件

#### 时间约束

| 约束 | 说明 |
|------|------|
| **交付节奏** | 按功能模块增量交付，非一次性大瀑布 |
| **构建验证** | 每次中型改动必须可构建验证，不允许长时间不可编译 |
| **Proto 变更时效** | proto 文件变更后，三端 codegen 必须在同一构建周期内完成 |
| **迭代周期** | 以 Phase 为单位迭代（1 Phase = 1~3 个并行任务 = 1 个验收点） |

#### 人力约束

| 约束 | 说明 |
|------|------|
| **团队构成** | 1 人（业务决策者/PM）+ AI Agent 军团（实现/测试/审查） |
| **PM 职责** | 需求解读、功能决策、验收确认 — 不做技术实现 |
| **Agent 能力** | 技术实现全部由 SubAgent 完成，PM 只回传必要结果 |
| **并行上限** | 最大 3 个 SubAgent 并行（资源受限，非无限） |

#### 遗留代码约束

| 约束 | 说明 | 影响 |
|------|------|------|
| **DSBridge-Android 已停维** | 原依赖 wendux/DSBridge-Android，JitPack 解析不稳定 | 被迫迁移到 happydog-intj/JsBridge，源码本地集成 |
| **AGP 9.x 内置 Kotlin** | AGP 9.0.1 内置 Kotlin 2.2.10，不能重复应用 kotlin-android 插件 | KSP 版本必须匹配 `2.2.10-2.0.2`，需特殊 `gradle.properties` 配置 |
| **鸿蒙 AOP 能力弱** | 鸿蒙端不支持编译期注解处理 | 鸿蒙用构造注入替代注解，与 Android 方案对等但不同构 |
| **继承模式遗留** | 原 `MPBridgeWebView` 为 open class，业务方继承使用 | 重构为 final + 组合模式，需迁移所有子类 |

## 2. 流程：双轨制

### 2.1 正向轨：新需求 → SSD

```
用户需求（自然语言描述）
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 1: 需求结构化                                       │
│  PM Agent 解读 → 采访澄清 → proposal.md                    │
│  输出：功能模块列表 + 模块职责 + 输入/输出                     │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 2: 接口定义                                         │
│  每个模块 → 类型定义 + 函数签名 + 调用示例                      │
│  输出：proposal.md §3 接口定义                              │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 3: 任务拆分（DAG）                                    │
│  每个任务 → 独立 md 描述：目标 + 上游依赖 + 下游影响 + 验收标准  │
│  输出：proposal.md §4 任务清单 + DAG 依赖图                   │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 4: DAG 调度执行                                      │
│  按依赖拓扑排序 → 并行 SubAgent → 文件传递上下文               │
│  规则：无依赖可并行 / 同 Phase 内无数据依赖 / 阶段验收         │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 5: 验收交付                                          │
│  Test SubAgent 验证 → 文档同步 → Git 提交 → 产物归档          │
└──────────────────────────────────────────────────────────┘
```

**关键产物链路**：
```
用户需求 → proposal.md（需求真相源）→ 任务 md（执行指令）→ 代码产物 → 测试报告 → 验收通过
```

### 2.2 逆向轨：老项目 → AI 理解 → Skills 沉淀

当面对一个已有代码库（非从零开始）时，SSD 采用逆向工程流程：

```
已有代码库
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│  Step 1: AI 读懂工程                                        │
│  Search SubAgent 全量扫描 → 识别模块边界/依赖/技术栈           │
│  输出：模块依赖图 + 技术栈清单 + 关键文件索引                   │
│  工具：Agent(Search) + SearchMemory                          │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Step 2: 架构抽取                                            │
│  分析设计模式/通信协议/数据流 → 形成架构文档                     │
│  输出：Design.md（架构真相源）+ Wiki.md（变更历史）             │
│  工具：Agent(Search) + Read + Write                          │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Step 3: 知识沉淀                                            │
│  提取可复用的模式/约定/踩坑经验 → 写入 Memory + 文档            │
│  输出：                                                      │
│    - Memory 系统：编码规范/技术选型/构建配置/踩坑经验           │
│    - 文档：constraints.md（约束）+ capabilities.md（能力）     │
│  工具：UpdateMemory + Write                                  │
└────────────────────┬─────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────────────┐
│  Step 4: Skills 封装                                         │
│  将高频操作封装为可复用的 Skill / SubAgent 模板                 │
│  输出：自定义 Skill（如 bridge-test, proto-validate）          │
│  工具：/create-skill + /create-subagent                      │
└──────────────────────────────────────────────────────────┘
```

**逆向轨实际案例（MP-SDK 自身）**：

MP-SDK 项目本身就是逆向轨的产物。AI Agent 在接手该项目时：

| 步骤 | AI 执行的操作 | 产出 |
|------|-------------|------|
| 读懂工程 | 全量扫描三端代码，识别 Proto 驱动架构、KSP 注入、dsBridge 兼容协议 | 模块依赖图、关键文件清单 |
| 架构抽取 | 分析 Design.md（989行）、Wiki.md、propersal.md 中的设计决策 | 架构真相源确认 |
| 知识沉淀 | 提取 AGP 9.x 兼容方案、命名约定、构建流程等经验 | Memory 系统 30+ 条记忆 |
| Skills 封装 | 将构建验证、Proto 变更等操作标准化 | specsv2/capabilities.md |

### 2.3 双轨制协同

```
         ┌─── 逆向轨（老项目）──── 产出知识 ───┐
         │                                    │
         ▼                                    ▼
   已有代码库                           知识 & Skills
         │                                    │
         │              正向轨                  │
         └─────────── 新需求 ──────────────────┘
                       │
                       ▼
              proposal.md → DAG → 执行 → 验收
                       │
                       ▼
                 新代码 + 新知识（沉淀回 Memory）
```

**双轨切换条件**：

| 条件 | 执行轨道 |
|------|---------|
| 全新项目 / 新增独立模块 | 正向轨 |
| 接手已有项目 / 理解遗留代码 | 逆向轨 |
| 在已有项目上新增功能 | 逆向轨（先理解）→ 正向轨（再实现） |
| 重构 / 架构升级 | 逆向轨（先理解现状）→ 正向轨（再规划） |

## 3. 质量保障：测试 SubAgent 军团

### 3.1 军团编制

```
PM Agent（指挥官）
    │
    ├── Test SubAgent × N（测试军团）
    │   ├── Build Tester：编译构建验证
    │   ├── Artifact Checker：生成产物校验
    │   ├── Integration Tester：端到端集成验证
    │   └── Regression Tester：回归测试（全量构建）
    │
    ├── Implement SubAgent × N（实现军团）
    │   └── 按模块分配：Android / HarmonyOS / Web / Codegen
    │
    ├── Review SubAgent × 1（审查官）
    │   └── 代码审查 + 架构合规检查
    │
    └── Search SubAgent × 1（情报官）
        └── 信息收集 + 影响评估 + 依赖分析
```

### 3.2 全程参与机制

测试军团不是最后才介入，而是从需求阶段就参与：

| 阶段 | 测试军团角色 | 具体动作 |
|------|------------|---------|
| **需求分析** | 验收标准制定者 | 为每个任务定义可测量的验收标准 |
| **任务编排** | 测试计划制定者 | 确定每个 Phase 的测试策略和触发时机 |
| **执行实现** | 即时验证者 | 每个 SubAgent 完成任务后立即触发 L1 编译测试 |
| **阶段验收** | 阶段关卡 | Phase 结束时执行 L2/L3 测试，ACCEPTED 才放行 |
| **交付** | 最终验收者 | 执行 L4 全量回归测试，确保无破坏性变更 |

### 3.3 测试分层详解

```
L4 回归测试（全量构建，发版前）
    └── npm run build:all → 三端全部通过
    └── 示例应用全部可运行

L3 集成测试（Phase 结束）
    └── Android: 示例 App 运行 + 数据推送验证
    └── 鸿蒙: 示例页面运行 + JSBridge 通信验证
    └── Web: 装饰器阻塞/释放 + 拦截器注入验证

L2 单元测试（功能模块完成）
    └── Proto 解析器: 输入 .proto → 输出正确的 AST
    └── 命名推导: PascalCase → camelCase / sync / UPPER_SNAKE
    └── DataSyncManager: pushData → waitForData → 数据正确

L1 编译测试（每次代码变更）
    └── gradlew.bat assembleRelease → BUILD SUCCESSFUL
    └── hvigorw.js assembleHar → BUILD SUCCESSFUL
    └── npm run build → 无错误
```

### 3.4 Test SubAgent 回传规范

```
回传格式（< 500 字）：
┌─────────────────────────────────────┐
│ 任务: T{n} 验收                       │
│ 编译测试: PASS                        │
│ 产物检查: PASS（DataSyncBindings.kt   │
│   包含 3 个通道映射）                  │
│ 示例验证: PASS（WebView 加载正常）     │
│ 总体结论: ACCEPTED                    │
└─────────────────────────────────────┘

如 REJECTED：
┌─────────────────────────────────────┐
│ 任务: T{n} 验收                       │
│ 编译测试: FAIL                        │
│ 错误: KSP 版本不匹配                  │
│   kotlin-2.2.10 requires ksp-2.2.10  │
│ 总体结论: REJECTED                    │
│ 修复建议: 更新 libs.versions.toml     │
│   中 ksp 版本为 2.2.10-2.0.2          │
└─────────────────────────────────────┘
```

## 4. 约束与规范

### 4.1 三类约束总览

详见 [constraints.md](constraints.md)，核心约束如下：

#### 项目约束

| 约束 | 红线 |
|------|------|
| 构建入口统一 | 根目录 `package.json` npm scripts 为唯一入口 |
| Proto 唯一真相源 | 所有数据通道定义集中在 `specs/proto/` |
| 产物规范 | 统一输出到 `output/` 目录 |
| 不引入 PowerShell | 构建脚本跨平台兼容 |

#### 技术栈约束

| 平台 | 核心约束 |
|------|---------|
| Android | AGP 9.0.1 + Kotlin 2.2.10 + KSP 2.2.10-2.0.2，禁止 JitPack/继承/反射 |
| 鸿蒙 | DevEco 内置 node，禁止封装隐藏原生 Web 组件 |
| Web SDK | 零运行时依赖，Proto 仅作 Schema，传输用 JSON |
| Proto | 仅 message + 标量字段 + repeated，禁止嵌套/enum/oneof |

#### 团队约束

| 约束 | 说明 |
|------|------|
| SubAgent 回传 | 只回传状态+摘要（< 500字），大量信息通过文件传递 |
| 决策权限 | 仅功能和业务决策需人工确认，技术决策 Agent 自主完成 |
| 文档同步 | 每次重要变更需同步到对应 Markdown 文档 |

### 4.2 MCP/Skill 接入规范

详见 [capabilities.md](capabilities.md)，核心原则：

| 原则 | 说明 |
|------|------|
| Schema 先读 | 调用 MCP Tool 前必须先读取 JSON Schema |
| 不猜测参数 | 参数名/类型严格从 Schema 获取 |
| 能力矩阵 | 按任务类型推荐工具（代码实现/搜索/测试/部署各有所属） |
| 安全边界 | 写操作需确认，凭据不传递，审计日志记录 |

## 5. 结果与反思

### 5.1 量化收益

| 指标 | 数据 | 说明 |
|------|------|------|
| **三端代码一致性** | 100% | Proto 驱动 codegen，命名/接口/行为完全一致 |
| **新增通道耗时** | 3 步 | 加 proto message → build → 使用（无需改 SDK 源码） |
| **构建自动化** | 1 条命令 | `npm run build:all` 产出全部三端 SDK |
| **运行时开销** | 零反射 | Android 编译期 KSP 注入，无运行时反射开销 |
| **前端依赖** | 0 个 | 零运行时依赖，axios 为 peerDependency |
| **人工决策次数** | 极少 | 仅功能/业务决策需人工确认，技术实现全自动 |
| **上下文效率** | SubAgent 回传 < 500 字 | 大量信息通过文件传递，PM Agent 上下文不被撑爆 |
| **最大并行度** | 3 SubAgents | Phase 2/3 可并行执行三端实现任务 |

### 5.2 踩坑案例：AGP 9.x + KSP 版本兼容地狱

**背景**：项目使用 AGP 9.0.1（最新版），内置 Kotlin 2.2.10 编译器。需要引入 KSP 实现编译期注解处理。

**踩坑过程**：

```
第 1 次尝试：使用 ksp-2.0.21-1.0.27
  → 报错：ksp version is too old for kotlin-2.2.10
  → 原因：KSP 版本与 Kotlin 编译器版本不匹配

第 2 次尝试：升级到 ksp-2.2.10-1.0.27
  → 报错：Cannot add extension with name 'kotlin'
  → 原因：AGP 9.x 内置 Kotlin 插件，不能重复应用 kotlin-android

第 3 次尝试：不应用 kotlin-android，使用 KSP2 格式版本 2.2.10-2.0.2
  → 报错：Using kotlin.sourceSets DSL is not allowed
  → 原因：AGP 9.x 内置 Kotlin 不允许 KSP 使用 sourceSets DSL
  → 修复：gradle.properties 添加 android.disallowKotlinSourceSets=false

第 4 次尝试：编译通过，但 KSP 处理器模块报错
  → 报错：Inconsistent JVM-target: compileJava(11) vs compileKotlin(21)
  → 原因：data-sync-processor 的 Java/Kotlin JVM target 不一致
  → 修复：统一使用 JavaVersion.VERSION_21

最终方案：
  KSP 版本 = 2.2.10-2.0.2（格式：{kotlin-version}-2.0.{patch}）
  不应用 kotlin-android（使用 AGP 内置）
  gradle.properties 添加 disallowKotlinSourceSets=false
  JVM target 统一 21
```

**教训**：
1. AGP 9.x 的"内置 Kotlin"是一个重大变化，所有 Kotlin 相关插件版本必须与之匹配
2. KSP 版本号格式在 KSP2 时代变为 `{kotlin-version}-2.0.{patch}`，不是简单的语义版本
3. 这类版本兼容问题无法从文档中提前预知，只能通过"编译→报错→修复"循环解决
4. **将踩坑经验沉淀到 Memory 系统**，后续遇到相同问题可直接检索，避免重复踩坑

### 5.3 规范迭代历史

SSD 规范本身也经历了迭代演进：

| 阶段 | 规范状态 | 关键变化 |
|------|---------|---------|
| **v0（项目启动）** | 无规范 | 用户口头描述需求，AI 直接实现 |
| **v1（specs/）** | 需求文档 + 设计文档 | 引入 `propersal.md` 记录需求，`Design.md` 记录架构 |
| **v2（Wiki 追溯）** | 追加变更记录 | 架构重构时意识到需要记录变更历史 → `Wiki.md` |
| **v3（specsv2/）** | SSD 规范驱动 | 系统性拆分为 proposal/constraints/harness/capabilities 四文档 |
| **v4（双轨制）** | 逆向轨补充 | 意识到老项目需要先理解再实现，补充逆向流程 |
| **v5（当前）** | 全景概述 | 添加 overview.md 回答完整的 SSD 方法论问题 |

**迭代驱动因素**：

```
问题驱动 → 规范演进
  ├── "SubAgent 回传内容太多撑爆上下文" → 添加回传规范（< 500字 + 文件传递）
  ├── "三端命名不一致导致联调失败" → 引入 Proto 驱动 Codegen（唯一真相源）
  ├── "继承模式导致 SDK 被覆盖" → 重构为组合模式 + KSP 注入
  ├── "每次都要问很多问题" → 规范采访规则（每次一问，仅功能决策）
  ├── "老项目不知道怎么下手" → 补充逆向轨流程
  └── "文档太散找不到" → 添加 overview.md 全景索引
```

### 5.4 方法论总结

**SSD 的核心公式**：

```
SSD = 需求结构化（proposal）
    + 约束明确化（constraints）
    + 执行军事化（harness + DAG + SubAgent）
    + 能力标准化（capabilities）
    + 知识持续化（Memory + 文档迭代）
```

**与传统开发方法的对比**：

| 维度 | 传统方式 | SSD 方式 |
|------|---------|---------|
| 需求表达 | 需求文档（静态） | proposal.md + DAG（可执行） |
| 任务分配 | 人工分配，会议协调 | PM Agent 自动拆分，DAG 调度 |
| 上下文管理 | 全在脑子里 | SubAgent < 500 字回传 + 文件传递 |
| 质量保障 | 最后测试 | Test SubAgent 全程参与（需求→验收） |
| 知识管理 | Wiki（容易过时） | Memory 系统 + 文档自动同步 |
| 可复用性 | 人脑记忆 | Skills + SubAgent 模板 + Memory |
